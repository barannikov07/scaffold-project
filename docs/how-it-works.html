AGENTS.md · a map, not a manual · CLAUDE.md is a one-line import of it

Tripwires. Hard rules that must never break, one line each, pointing to the document that owns the detail. The owner named the first two in the interview; the third followed from "fees, eventually".

  • Attendance records are append-only: never edited or deleted once a rehearsal has happened → infra.md (Data model)
  • A singer never sees another singer's phone number or email address → infra.md (Roles inside the app)
  • Membership fees go through Stripe; card details are never stored by us → infra.md (External services)

Plus a "read before working" table (task → document), eight golden rules that point to workflow.md, the owner profile, and the directory map. Nothing else. Detail lives in the documents it points to.

docs/vision.md · the prism every PRD is checked against

The end state. Every rehearsal lives in ChoirHub before it happens. Every singer opens the app and knows, without asking anyone, when the next rehearsal is and what to prepare. The conductor opens the app the evening before and sees exactly who will be in the room and which sections will be thin, instead of counting replies in a WhatsApp group. Running the choir stops being an evening of admin and becomes a few minutes inside one app.

Principles that settle trade-offs.

  • The conductor's time is the scarcest resource.
  • A singer must do their whole job on a phone, in under a minute, half-distracted.
  • The record of what happened is sacred: written once, corrected by a new entry, never rewritten.
  • A singer's contact details belong to the singer.
  • Boring and reliable beats clever. This replaces a WhatsApp group.

Drafted by Claude from the interview, explicitly labelled a first draft for the owner to argue with. Changes go through a recorded decision and a changelog row.

docs/decisions.md · append-only, numbered, cited from other docs

D-001 · tech · Active. Stack: Next.js, Postgres (Supabase), Supabase Auth (email link and Google), hosted on Vercel. The owner already had Vercel and GitHub accounts, and that decided the hosting. Sign-in comes with the database so it is not a second account or a second bill. Rejected: a native phone app (app-store accounts and review queues for a non-technical owner), a separate auth provider, a spreadsheet or no-code tool (neither survives "attendance is append-only" and "contact details hidden per role").

D-002 · process · Active. Adopt the nine-stage pipeline, the planning stack, and ship-only-via-git.

D-003 · product · Active. Three invariants from day one, recorded as tripwires before any code exists, because each is cheap to design for and expensive to retrofit.

docs/products/rehearsal-rsvp/prd.md · drafted, stopped at the approval gate

The PRD is written in the owner's language: problem, users, scope, six non-goals, flows, six success criteria, and a vision-fit section that quotes the vision. It ends with the questions the owner must answer before saying "approved":

  1. How do singers get into ChoirHub in the first place? The feature is meaningless without members who can sign in. Recommendation: the conductor adds each singer, kept as thin as possible.
  2. Can singers see who else is coming, or only the conductor? Recommendation: singers see counts, the conductor sees names.
  3. How often does the choir rehearse, and is creating each one by hand acceptable for now?
  4. Are the voice sections soprano, alto, tenor, bass, or does your choir divide differently?
  5. How far ahead do singers need to see: the next rehearsal or the whole term?
  6. Is the place just a line of text, or does it need an address, a map link, a note like "side door, ring the bell"?
infra.md · the technical knowledge base, living

Eight sections, each opening with one plain sentence for the owner: stack at a glance, environments, identities and access (accounts, app roles, test identities, env var names only), data model (entity diagram), key flows (sequence diagrams), external services, operations, constraints and gotchas.

How Claude builds

The strongest model thinks. Cheaper models type.

Thinking and building are different jobs. One orchestrator writes the PRD and spec, splits the work into file-scoped items, briefs builders, and reviews every diff. The loop stops after two rounds.

Orchestrator

  • Interviews, assesses, writes the PRD and the spec
  • Splits the spec into independent, file-scoped work items
  • Briefs one builder per item, in parallel; builds small things itself
  • Reviews every diff against the spec and tripwires; runs verify and the test plan
  • Returns only confirmed correctness or security findings; fixes style inline
  • Stops after two rounds. Remaining blockers mean the plan is wrong, and the owner hears it

Builders

  • One work item each, from a self-contained brief: files, contract, done-criteria, tripwires, how to verify
  • Work on a branch or worktree; run the tests they were given
  • Report what changed, not "done"
  • Never widen scope, change the spec, or merge

Done means

  • Verify script passes and the test plan was executed
  • Zero confirmed critical findings
  • Guide, index, roadmap, and infra.md are true
  • Not "the reviewer ran out of things to say"

Tracking without drift

Four altitudes, one fact each.

Progress tracking fails when one document holds plan, status, history, and reasoning at once. So they are split, and each links downward.

Whydocs/vision.md

"Running the choir stops being an evening of admin and becomes a few minutes inside one app."

Changes only through a recorded decision. Every PRD has a vision-fit section that quotes it; a conflict is resolved by dropping the PRD or amending the vision, never silently.

What, in what orderdocs/roadmap.md

Milestones 0 to 4 in one table. The first row not marked Done is "now". Shipped rows keep their dates.

Fluid by design: one-line rows, PRDs written one milestone ahead at most, reorders logged with a decision link.

Where each piece standsdocs/product-index.md

Tech setup · milestone 0 · Planned. Rehearsals and RSVPs · milestone 1 · Planned. Stage changes at every transition: Idea, Planned, PRD, Spec, In build, In QA, Live.

If the table and reality disagree, the table is fixed in the same change. /status reads it aloud and lists every open TBD.

Why it is this waydocs/decisions.md

D-001 stack · D-002 process · D-003 tripwires. Numbered so a PRD can cite them; append-only so a reversal is a new entry, never an edit.

The test for an entry: would a future owner, or a fresh Claude session, wonder "why is it like this?"
